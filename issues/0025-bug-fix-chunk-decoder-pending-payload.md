# fmt0 受信時に未完了メッセージのペイロードを破棄する

- Created: 2026-11-22
- Completed: {YYYY-MM-DD}
- Branch: feature/fix-chunk-decoder-pending-payload
- Polished: {YYYY-MM-DD}

## 目的

同じチャンクストリームで受信中のメッセージがある状態で fmt0 チャンクを受信したときに、旧メッセージのペイロードが新しいメッセージに混入しないようにする。

## 現状

- `src/rtmp_chunk_decoder.rs` の `RtmpChunkDecoder::decode` は、既存の `RtmpChunkStream` を clone してメッセージヘッダーを適用する。
- `decode_message_header` の fmt0 分岐は `message_size`、メッセージ型、メッセージストリーム ID、タイムスタンプを上書きするが、`acc_payload` をクリアしない。
- `decode_message_payload` は `message_size - acc_payload.len()` を残りバイト数として扱うため、旧メッセージの受信済みペイロードが新しいメッセージの先頭に連結される。
- RTMP 仕様 5.3.1.2 節では、fmt0 は常に新しいメッセージの開始である。同じチャンクストリームで未完了のメッセージを新しいメッセージに連結してはならない。

### 再現条件

1. `RtmpChunkDecoder` のチャンクサイズを 4 に設定する。
2. fmt0 のチャンクで、メッセージサイズ 10、メッセージ型 18（Data AMF0）、メッセージストリーム ID 0 として 4 バイト `[1, 2, 3, 4]` を渡す。メッセージは未完のため `None` が返る。
3. 同じチャンクストリームに fmt0 のチャンクで、メッセージサイズ 6、メッセージ型 18、メッセージストリーム ID 0 として `[9, 9, 7, 7, 7, 7]` を渡す。

期待は新しいメッセージのペイロード `[9, 9, 7, 7, 7, 7]`。実際は `[1, 2, 3, 4, 9, 9]` になり、残りの 4 バイトが次のチャンクヘッダーとして解釈される。

メッセージサイズ 128 の新しいメッセージに対して、旧メッセージの 128 バイトを受信済みの状態で 1 バイトも受信せずに fmt0 を送ると、旧 128 バイトをペイロードとするメッセージが返る。
旧ペイロードが新しい message_size より長い場合は `invalid_data("accumulated payload exceeds message size")` になり、同じチャンクストリームが恒久エラーになる。

## 設計方針

- fmt0 のメッセージヘッダーを適用するときに `acc_payload` を破棄する（仕様準拠モデル）。
- もしくは、未完了メッセージがある状態で fmt0 を受信した場合に `ErrorKind::InvalidData` を返す。
- どちらを採用する場合も、旧ペイロードを新しいメッセージに連結しないことを不変条件とする。
- `reset_chunk_stream` を使う Abort の経路と、通常の fmt0 の経路で挙動が一貫していることを確認する。

## 完了条件

- 上記の再現条件で新しいメッセージのペイロードが `[9, 9, 7, 7, 7, 7]` になる、または明示的にエラーになる。
- 旧ペイロードが新しい message_size より長い場合に、暗黙の連結や恒久エラーが発生しない。
- 既存のチャンク分割受信と拡張タイムスタンプのテストに回帰がない。
- 上記を確認する単体テストを追加する。

## 解決方法

1. `src/rtmp_chunk_decoder.rs` の fmt0 処理で `acc_payload` をクリアする、または未完了状態を検出してエラーにする。
2. 上記 2 ケースの単体テストを追加する。
3. 既存の chunk テストと接続層の回帰テストを実行して確認する。

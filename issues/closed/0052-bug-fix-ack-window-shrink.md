# 確認応答ウィンドウを縮小したら同じ受信処理で ACK を送る

- Created: 2026-11-25
- Completed: 2026-11-25
- Branch: feature/fix-ack-window-update
- Polished: 2026-11-25

## 目的

相手が確認応答ウィンドウを小さい値に変更したとき、すでにその窓分を受信していれば、次の受信を待たずに ACK を返す。相手が ACK 待ちのまま停止し得る状況を減らす。

## 現状

`rtmp_connection` の `RtmpMessageChannel::feed_recv_buf` は、受信バイト数を加算し、前回 ACK 送信時からの未確認量が `peer_ack_window_size` の半分を超えたら ACK の値を返す。`peer_ack_window_size` を変更する `set_peer_ack_window_size` は、`rtmp_client_connection` と `rtmp_server_connection` が `WinAckSize` を受信メッセージとして処理するときに呼ぶ。

このため、`WinAckSize` の受信と同じ呼び出しで ACK の判定を行うと、変更前の大きいウィンドウで判定してしまう。窓を縮小した時点で未確認量が新しい半分の閾値を超えていても、次の `feed_recv_buf` が呼ばれるまで ACK を返さない。

[Adobe RTMP 仕様（2012 年 12 月版）§5.4](https://veovera.org/docs/legacy/rtmp-v1-0-spec.pdf#page=18) はプロトコル制御メッセージが受信時に有効になるとし、[§5.4.3–5.4.4](https://veovera.org/docs/legacy/rtmp-v1-0-spec.pdf#page=20) は通知されたウィンドウ分を受信したら ACK を送ることを MUST とする。

### 再現条件

1. 接続を確立し、初期の `WinAckSize` を大きい値にする。
2. 小さい値の `WinAckSize` を最後に受信したときの未確認量が、このメッセージ自身のチャンクバイトを含めて「新しいウィンドウの半分（整数除算）より大きく、変更前のウィンドウの半分（整数除算）以下」になるように、その手前でデータを受信する。
3. その `WinAckSize` を渡す。同じ受信呼び出しの終了時点では、送信バッファに ACK が積まれない。空の入力を渡して初めて ACK が積まれる。

## 設計方針

- `RtmpMessageChannel` に、ウィンドウの設定と ACK 要否の再判定を行う内部処理を追加する。`WinAckSize` を受信したクライアントとサーバーは、`set_peer_ack_window_size` の代わりにこの処理を呼ぶ。
- 再判定では、現在の計数起点と「未確認量がウィンドウの半分を超えたら送る」判定をそのまま使う。すでに同じ累計値を ACK として積んでいる場合は重複して積まない。
- 受信 ACK の値や欠落を送信可否・接続状態の判定に使わない現在の方針は変更しない。公開シグネチャは変更しない。
- ウィンドウの適用時期や半窓で送る方針の仕様が変わった場合は、この判定を見直す。

## 完了条件

- 双方の公開 API で、未確認量が新しいウィンドウの半分（整数除算）を超える縮小をした場合に限り、同じ受信呼び出しの終了時点で ACK が送信バッファに積まれ、その累計値が正しい。新しいウィンドウの半分以下なら、縮小だけでは ACK を積まない。
- 窓の縮小で ACK を積んだ直後に、追加の受信がない空入力を渡しても、同じ累計値の ACK を重複して積まない。
- 1 回の入力に複数のウィンドウ変更が含まれる場合、最後に適用したウィンドウで次回の判定を行う。
- 上記を公開 API の性質テストで検証する。

## 解決方法

1. `RtmpMessageChannel` に `handle_win_ack_size` を追加し、ウィンドウを適用した直後に既存の ACK 要否の判定を再実行して、必要なら ACK を送信バッファへ積むようにした。クライアントとサーバーの `WinAckSize` 処理は、この処理を呼ぶように変更した。
2. 計数起点、半窓で送る判定、受信 ACK を送信可否や接続状態に使わない方針は変更していない。`set_peer_ack_window_size` は公開 API として残し、設定だけを行うことを doc に明記した。
3. 公開 API の性質テストで、縮小と同じ受信呼び出しでの ACK、半窓以下と等号で送らないこと、空入力で同じ累計値を重複しないこと、複数のウィンドウ変更では最後の値で次回判定することを検証した。再判定を外す変異、常に ACK を送る変異、計数起点を更新しない変異で、テストが失敗することも確認した。

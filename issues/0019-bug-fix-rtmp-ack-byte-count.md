# RTMP ACK の計数起点の違いによる誤切断を修正する

- Created: 2026-11-21
- Completed: 2026-11-21
- Branch: feature/fix-rtmp-ack-byte-count
- Polished: 2026-11-21

## 目的

ハンドシェイクのバイト数を ACK に含める相手と通信しても、正常な ACK を欠落と誤判定して配信や再生を止めないようにする。

## 現状

- クライアント接続の `RtmpClientConnection::advance_send_buf` とサーバー接続の `RtmpServerConnection::advance_send_buf` は、ハンドシェイクの送信分をメッセージチャネルの送信累計に含めない。ハンドシェイクは片方向で `1 + 1536 + 1536 = 3073` バイトある。
- メッセージチャネルの `RtmpMessageChannel::notify_ack_received` は相手の ACK をそのまま記録する。`RtmpMessageChannel::advance_send_buf` は `total_bytes_sent.wrapping_sub(last_ack_received)` が ACK ウィンドウの 2 倍を超えると `false` を返し、接続側は `Disconnecting` に遷移する。現行の 2 倍の計算は `u32` なので、ウィンドウが `2^31` バイト以上の場合は表現範囲を超える。
- YouTube への配信で、ハンドシェイクを含む ACK が観測され、長時間配信が止まったと報告された。計数差による誤判定は以下の条件で説明でき、累計 4 GiB への到達は必要ない。報告された停止時点での生の ACK 値と実送信量は未確認。

### 再現条件

1. ACK ウィンドウを 5,000,000 バイトとし、ハンドシェイク後の RTMP チャンクを合計 5,000,000 バイト送信する。
2. 相手がハンドシェイク込みで全量を受信し、`sequence_number = 5_003_073` の ACK を返す。
3. その ACK の処理後に送信済みとしてさらに 1 バイト進めると、未確認分は実際には 1 バイトだが、現行処理は 4,294,964,224 バイトと判定して切断状態に遷移する。

## 設計方針

- [Adobe RTMP 仕様（2012 年 12 月版）§5.4.3–5.4.4](https://veovera.org/docs/legacy/rtmp-v1-0-spec.pdf#page=20) は ACK のシーケンス番号を 32 ビットの累計受信バイト数と定義するが、ハンドシェイクを含めるか、折り返しをどう扱うかは明記していない。片方向のハンドシェイク長は [同仕様の §5.2.2–5.2.4](https://veovera.org/docs/legacy/rtmp-v1-0-spec.pdf#page=7) による。[FFmpeg の内蔵 RTMP 実装](https://github.com/FFmpeg/FFmpeg/blob/master/libavformat/rtmpproto.c) はハンドシェイク後に `bytes_read` を初期化し、[OBS 同梱の librtmp](https://github.com/obsproject/obs-studio/blob/master/plugins/obs-outputs/librtmp/rtmp.c) はハンドシェイク受信分も含む `m_nBytesIn` を ACK に書き込む。
- クライアントとサーバーが共有する `RtmpMessageChannel` で受信 ACK の解釈を修正する。基準はハンドシェイク後の送信累計とする。クライアント・サーバーとも、最初のチャンク送信を集計する前、かつ受信した最初の ACK を処理する前に、実際に送信したハンドシェイク長を一度だけ内部登録し、込みの起点を有効にする。サーバー側では送信バッファが空になる時点と `C2` 受信によって `is_send_complete()` が `true` になる時点が異なるため、送信処理中の同メソッドの変化だけに依存しない。`RtmpMessageChannel` を単体で利用する場合は従来どおりチャンクのみを数える。
- 通信上の ACK は `u32` のままとし、送信累計、最後に受理した ACK の復元値、起点ごとの確認済み位置は `u64` で保持する。受信した ACK を下位 32 ビットに持つ累計値を、最後に受理した値（初期値は 0）から、チャンク送信累計と送信済みハンドシェイク長の合計までの範囲で探す。一意に復元できない値や、最後に受理した値と同じ値は進捗に数えない。
- 復元値から起点ごとのオフセット（0 またはハンドシェイク長）を差し引き、チャンク送信済みの範囲内で、かつその起点の前回の確認済み位置より先なら更新する。少なくとも一方の確認済み位置が進んだ場合だけ、復元値を最後に受理した ACK として記録する。
- 最初の ACK などから起点を決め打ちせず、起点ごとに保持した確認済み位置から未 ACK 量を求める。いずれかの起点で未 ACK 量が閾値以内なら切断しない。これは厳密な未 ACK 量を特定するためではなく、起点の違いによる誤切断を避けるための判定とする。すべての起点で未 ACK 量が閾値を超えた場合に限り、従来の切断判定に進む。閾値はウィンドウの 2 倍のままとし、`u64` で計算する。
- 公開 API と自分が送る ACK の計数起点は変更しない。他実装固有のカウンターリセットは対象外とする。

## 完了条件

- 上記の再現条件と、ハンドシェイクを含めない相手との通信で、正常な ACK により切断状態へ遷移しない。両起点に対応付け可能な ACK の後に、ハンドシェイク込みの起点にしか対応付けできない正常な ACK が届く場合も、確認済み位置が進んで切断されない。
- 両方の計数起点で、32 ビットの折り返しをまたいでも一意に復元できる ACK は確認済み位置を進める。生の 32 ビット値が過去の ACK と同じでも、新しい周回の位置に一意に復元できる場合は進捗に数える。どの起点でも有効な位置に対応しない ACK、最後に受理した ACK と同じ累計位置にしか復元できない ACK、複数周回に対応する ACK では確認済み位置を進めない。チャネルの単体利用ではハンドシェイク長を加味せずに判定する。
- 両起点の未 ACK 量のうち片方だけが閾値を超えた場合は切断せず、ACK が途絶えてすべての起点で閾値を超えた場合は引き続き検出する。大きなウィンドウでも閾値の計算があふれない。これらを大量の転送なしで回帰テストする。

## 解決方法

- `RtmpMessageChannel` は最後に確認できた ACK を基準に 32 ビット値を復元し、送信済み範囲で一意に決まる位置を優先する。起点ごとの確認済み位置と送信累計を `u64` で管理し、どちらの起点でも未確認量が閾値を超えた場合にだけ切断判定に進む。
- クライアントとサーバーは送信したハンドシェイクの長さを内部登録する。ハンドシェイク送信完了の通知前に届いた ACK はチャンクの確認に使わない。公開 API と送出する ACK の算出方法は変更していない。
- 送信済み範囲にまだ達していない ACK は、受信時点の送信バッファに対応する位置だけを保留し、部分送信の通知に応じて確定する。保留だけの値は後続 ACK の復元基準に使わない。ハンドシェイク完了後に ACK の起点を区別できない場合は誤切断を避けるため、ACK 途絶の検出が計数差の分だけ遅れる場合がある。
- 32 ビットの折り返し、重複・範囲外の値、閾値の境界、送信通知より先に届いた ACK を単体テストで検証した。クライアントとサーバーのハンドシェイク込み ACK と、C2 の送信通知前に届いた ACK も公開 API の回帰テストで検証した。

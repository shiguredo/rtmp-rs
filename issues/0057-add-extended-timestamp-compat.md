# 拡張タイムスタンプを省略する相手との互換設定を追加する

- Completed: {YYYY-MM-DD}
- Branch: feature/add-extended-timestamp-compat
- Polished: {YYYY-MM-DD}

## 目的

形式 3 のチャンクで拡張タイムスタンプを省略する送信側から受信したとき、チャンクの境界がずれてメッセージを誤解釈しないようにする。需要が確認できた場合に、既定の挙動を変えない明示的な互換設定として追加する。

## 現状

`rtmp_chunk_decoder` の `RtmpChunkDecoder::decode_message_header` は、形式 3 のチャンクで、同じチャンクストリームの直近の形式 0〜2 のチャンクが拡張タイムスタンプを持っていた場合に 4 バイトを読み取る。

[Adobe RTMP 仕様（2012 年 12 月版）§5.3.1.3](https://veovera.org/docs/legacy/rtmp-v1-0-spec.pdf#page=16) は、この場合に形式 3 にも拡張タイムスタンプが存在すると定義している。現行実装はこの定義に従っている。

一方で、拡張タイムスタンプが必要な条件でも、新しいメッセージの先頭となる形式 3 のチャンクでは 4 バイトを付けず、継続チャンクには付ける送信側が存在する。この送信側から受信すると、デコーダーは後続の 4 バイトをタイムスタンプとして読み取り、チャンクの境界とペイロードを誤解釈する。後続の 4 バイトはペイロードとも解釈できるため、受信データだけから省略の有無を自動判定することはできない。

### 再現条件

1. 拡張タイムスタンプを持つ形式 0 のチャンクを受信し、そのチャンクストリームで拡張タイムスタンプが有効な状態にする。
2. 同じチャンクストリームで、新しいメッセージの先頭として拡張タイムスタンプを省略した形式 3 のチャンクを送る。
3. 続けてそのメッセージのペイロードを送る。

現行は 2 の直後の 4 バイトをタイムスタンプとして消費するため、3 の解釈がずれる。

## 設計方針

- 省略を受け入れるかどうかを、利用側が明示的に設定できるようにする。既定は仕様どおり「形式 3 にも拡張タイムスタンプがある」とする。
- 設定を有効にした場合は、新しいメッセージの先頭となる形式 3 のチャンクでは拡張タイムスタンプを読まず、継続チャンクでは読む。どちらも同じチャンクストリームの直前のヘッダー情報を引き継ぐ。
- 受信データからの自動判定は行わない。誤解釈の危険があり、ペイロードの内容に依存するため。
- 設定は受信側だけに作用させ、送信するチャンクの形式は変更しない。
- 既定値を変更する需要が確認できた場合は、この方針を見直す。着手前に、対応が必要な送信側の存在と再現条件を確認する。

## 完了条件

- 既定の設定では、形式 3 の拡張タイムスタンプを仕様どおり読み取る現行の挙動に回帰がない。
- 設定を有効にすると、新しいメッセージの先頭で拡張タイムスタンプを省略した形式 3 のチャンクを、ペイロードをずらさずに受信できる。
- 設定を有効にしても、継続チャンクの拡張タイムスタンプは読み取る。
- 上記を公開 API の性質テストで検証する。

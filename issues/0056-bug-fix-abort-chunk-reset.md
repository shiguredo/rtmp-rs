# Abort 後も圧縮済みチャンクの受信を継続する

- Created: 2026-11-25
- Completed: {YYYY-MM-DD}
- Branch: feature/fix-abort-chunk-reset
- Polished: {YYYY-MM-DD}

## 目的

`Abort` で受信途中のメッセージを破棄した後、同じチャンクストリームで圧縮ヘッダーを使う後続メッセージを、接続エラーにせず受信できるようにする。

## 現状

`rtmp_chunk_decoder` の `RtmpChunkDecoder::reset_chunk_stream` は、指定したチャンクストリームの状態を `HashMap` から削除する。`rtmp_message_decoder` の `RtmpMessageDecoder::decode_next` は `Abort` メッセージをデコードするとこの処理を呼ぶ。

このため、`Abort` の後にそのチャンクストリームで形式 1〜3 のチャンクを受けると、`RtmpChunkDecoder::decode` が「最初のチャンクは形式 0 でなければならない」として `InvalidData` を返す。

[Adobe RTMP 仕様（2012 年 12 月版）§5.4.2](https://veovera.org/docs/legacy/rtmp-v1-0-spec.pdf#page=19) は、`Abort` を「チャンクストリーム上で部分的に受信したメッセージを破棄する」ための通知と定義している。圧縮ヘッダーの履歴を消すことや、続くチャンクを形式 0 に限定することは規定していない。[§5.3.1.2](https://veovera.org/docs/legacy/rtmp-v1-0-spec.pdf#page=14) は、形式 1〜3 が同じチャンクストリームの直前のチャンクの情報を引き継ぐとしている。

### 再現条件

1. 同じチャンクストリームで形式 0 のチャンクを送り、メッセージの一部だけを受信した状態にする。
2. そのチャンクストリームを対象にした `Abort` を送る。
3. 同じチャンクストリームで形式 1 か形式 3 のチャンクを送る。

現行は 3 で `InvalidData` になる。期待は 3 が受理され、直前のヘッダー情報を引き継いでメッセージを組み立てられること。

## 設計方針

- `Abort` の処理では、受信途中のペイロードだけを破棄し、最後に受信を開始したメッセージのタイムスタンプ、タイムスタンプ差分、メッセージ長、種別、メッセージストリーム ID、拡張タイムスタンプの有無を残す。
- 公開している `RtmpChunkDecoder::reset_chunk_stream` の契約は変更しない。`Abort` 専用の部分破棄を内部に追加し、`RtmpMessageDecoder` からはそちらを呼ぶ。
- `Abort` の後に形式 0 から始める送信側も引き続き受理する。
- 圧縮ヘッダーの履歴を破棄する現在の挙動が必要な利用者向けの互換 API は追加しない。
- 仕様が `Abort` 後の圧縮再開を明記した場合や、送信側の扱いが変わった場合はこの方針を見直す。

## 完了条件

- 公開 API で、形式 0 の途中まで受信した後に `Abort` を送り、同じチャンクストリームで形式 1 または形式 3 のチャンクを送ると、メッセージを正しく組み立てられる。
- `Abort` の対象外のチャンクストリームの状態が変わらない。
- `Abort` の後に形式 0 から始める既存の挙動に回帰がない。
- 上記を公開 API の性質テストで検証する。
